# Agent Note: Tavern 存档列表可读性——可读 autosave 名与逐存档简介

Status: implemented

[English](2026-09-14-tavern-save-list-ux.md) | 中文

## 问题

存档行赖以展示的两个事实对玩家都不友好。autosave 目录名是紧凑机器戳（`autosave-20260913-210351-453-2`）——存档页是玩家面对的「我在哪里」清单，每行身份却要人肉解码；且行上没有任何「那一刻发生着什么」：两行只差 auto/manual，「哪个是海港那晚」只能挨个载入试。

## 决策

**autosave 名读作本地时间、精确到秒**——`autosave-2026-09-14-01:22:28`，同秒真碰撞才加数字后缀（workspace.ts 的 `readableSaveName`；紧凑序号形态保留给工作空间根名——那是玩家不读的机器 id）。**存档行按目录写入时间排序、不按名字**：命名形态已经换过一次代，跨代的字典序是虚构——mtime 是环形裁剪依赖的年代无关权威（名字只作决胜次序键，保证确定性）。

**每个带戳存档记录简介——存档时刻的最后一条玩家消息**——记进边界账本（`TavernSaveStamp.summary`，截一条展示行的量），三个盖章点全部捕获：手动 `save()`、无尾代理的回合末 autosave、闸门后的记账 autosave。`listSaves` 逐行透出；存档页渲染为省略号的第三行（悬浮给全文），保存对话框渲染为名字与类型之间的中间行。

## 备选方案

**保留机器名、前端解码。** 客户端格式化让目录层不动，但把又一个引擎拥有的事实交到浏览器手里——而且目录名就是存档在盘上的身份（覆盖确认逐字匹配它）；解码会造成「显示一套、操作另一套」。

**解析两种命名成时间戳来混合排序。** 为比较而解析两种文法等于在身份之外再造第三个派生事实——顺序；目录自己就记着写入时刻。

**每存档一个旁车文件存简介。** 边界账本本就每个带戳存档恰有一行、且是载入路径的权威；第二个逐存档文件对读者没有任何新增。

## 后果

名字的时间段用 `:`（POSIX 合法；NTFS 无法承载——预期文件系统为 macOS/Linux）。autosave 行一眼自明，每个带戳行说得出当时在发生什么；环形裁剪在任何未来的命名变化下都按真实新旧。代价是 mtime 依赖：`listSaves` 现在对每个存档目录 stat 一次（N 个存档、每个一次 `statSync`——被环形上限加手动行数约束），未来任何整体重写存档目录（= 覆盖存档）的流程会被当作新的存档时刻。未盖戳的行——早于账本机制的存档与 `autosave()` 测试助手——简介为空，不做合成。
